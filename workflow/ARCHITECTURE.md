# 架构宪法（ARCHITECTURE.md）

> 本文件是所有架构设计与代码实现的**最高约束**。架构设计师、开发工程师、架构师 CR 三个角色必须严格遵守；CR 阶段将本文件的硬性规则作为 blocker 级检查项。

## 一、总体原则：设计与实现分离

| 层次 | 方法论 | 说明 |
|---|---|---|
| **设计层** | 严格 DDD | 限界上下文、聚合根、实体/值对象、领域事件、上下文映射 |
| **实现层** | 三层架构（非纯血 DDD） | 不强制 Repository 模式、聚合工厂等重型模式，落地为清晰的三层 |

设计文档（`03-design.md`）必须同时包含：
1. **领域模型**：限界上下文划分、聚合根/实体/值对象识别、领域事件清单
2. **三层映射表**：领域模型 → 具体落地到 API 层 / 业务层 / 外部依赖层的哪些模块

## 二、实现层三层架构定义

```
┌─────────────────────────────────────────────────┐
│ API 层（接入层）                                  │
│ 职责：入参校验（格式/必填/边界）                   │
│       防腐：隔离外部协议、DTO 变化                 │
│       参数转化：外部参数对象 → 业务层参数对象       │
│ 禁止：任何业务逻辑                                │
├─────────────────────────────────────────────────┤
│ 业务层                                           │
│ 职责：全部业务逻辑处理                            │
│ 拆分：可按项目实际继续拆分子层（业务层/基础层等）， │
│       由架构设计师在 03-design.md 中明确           │
│ 精简：非必要参数校验不写（信任 API 层已校验）       │
├─────────────────────────────────────────────────┤
│ 外部依赖层（DB / 三方服务 / 中间件）               │
│ 职责：参数转化 + 防腐（隔离外部 SDK/存储细节）      │
│       足够通用，可被多个业务复用                   │
│ 禁止：绝对不允许出现任何业务逻辑                   │
│ 精简：非必要参数校验不写（信任上层），保持精简      │
└─────────────────────────────────────────────────┘
```

## 三、三条硬性规则（CR blocker 项）

1. **单向调用**：只允许上层调用下层。禁止循环调用；禁止下层反向依赖上层（外部依赖层不允许 import 业务层的任何东西）。
2. **职责纯净**：业务逻辑只能出现在业务层。API 层只做校验 + 转化；外部依赖层只做转化 + 防腐。
3. **精简校验**：业务层与外部依赖层不做重复参数校验——上层已校验过的，下层直接信任，不做防御性重检。

## 四、各角色的执行要求

| 角色 | 要求 |
|---|---|
| 架构设计师 | 设计稿必须给出领域模型图 + 三层模块划分映射表；业务层内部如需再分层，必须明确命名与职责 |
| 开发工程师 | 实现前必读本文件 + `03-design.md` 的三层映射表，严格按层落代码 |
| 架构师 CR | 固定检查：① 有无循环依赖/下层调上层 ② 业务逻辑是否泄漏到 API 层或外部依赖层 ③ 下层是否冗余校验 ④ 外部依赖层是否足够通用 |
| 人工复验 | 交接文档（`07-cr-handoff.md`）中入口清单按层标注穿透路径，便于人工一眼看出分层是否干净 |
## 五、云端分布式部署约束（红线，CR blocker 项）

项目均为**云端分布式部署**，设计与代码中**严禁任何单机假设**：

| 反模式（禁止） | 正确做法 |
|---|---|
| 本地内存当分布式缓存（HashMap/ConcurrentHashMap/Caffeine 存共享状态） | 分布式缓存（Redis 等） |
| 本地文件系统存共享数据 | 对象存储 / 共享存储 / DB |
| 单机锁（synchronized/ReentrantLock）保护跨实例资源 | 分布式锁 |
| 单机定时任务（多实例重复执行） | 分布式调度 / 分布式锁抢占 |
| 内存态跨请求（ThreadLocal、实例字段存会话状态） | 无状态设计，状态外置 |
| 非幂等接口（重试/重复投递产生脏数据） | 接口幂等设计 |

设计稿（03-design.md）必须显式说明：服务无状态方案、缓存选型、并发控制方案、幂等方案。

## 六、边界设计原则

架构与研发全过程必须**先想清楚边界再动手**：

1. **上下文边界**：限界上下文划分与业务语义一致，跨上下文协作只走防腐层/领域事件，不直接引用内部模型
2. **接口边界**：对外契约（入参/出参/错误码/幂等性）在设计稿中显式定义，契约之外不隐式依赖
3. **事务边界**：设计稿标注每个核心流程的事务范围，跨上下文/跨库不做隐式长事务，明确最终一致性方案
4. **数据边界**：每张表/每份缓存归属唯一的写方上下文，禁止多方直写同一份数据

## 七、工程规范：注释与日志

**注释要求：**
- 公共接口、复杂业务逻辑、非常规写法必须写注释；注释说明**为什么**（意图/约束/坑），而非复述代码
- 关键类与方法：职责一句话 + 参数/返回值约束

**日志要求（面向排查问题）：**
- 关键路径的入口、出口、分支决策点打日志；含业务标识（订单号/卡号等）便于链路追踪
- 异常日志必须带堆栈与上下文参数；catch 后不允许空吞
- 敏感信息（手机号/身份证号/密钥等）必须脱敏后输出
- 日志级别规范：ERROR=需立即处理，WARN=异常但可容忍，INFO=关键业务节点，DEBUG=排查细节（禁止在生产路径滥用 INFO 刷屏）
